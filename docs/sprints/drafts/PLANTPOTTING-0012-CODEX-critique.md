# PLANTPOTTING-0012 Claude Draft Critique

## Overall read

Claude's draft is strong and largely aligned with the brief. It correctly centers the 0.9661 pothos->Pilea failure, rejects margin-only abstention, sequences fixture sourcing before measurement, and keeps the Pilea mapping tied to a production boundary gate. Compared with my draft, it is more concrete in several executor-facing places, but it also overcommits on a default disambiguation design and introduces a few repo-specific claims and sourcing details that should be verified before becoming sprint instructions.

## What Claude's draft does better than mine

- `Repo anchors (verified, for the executor)` is stronger than my equivalent context. It names likely concrete files: `ModelScoreMapper.kt`, `model_manifest.json`, `plant_class_map.json`, `HousePlantClassMapValidationTest`, `species.json`, `app/build.gradle.kts`, and `docs/kb/ml-mapping-notes.md`. My draft stayed a little more generic in places where an executor benefits from direct file anchors.
- `Phase 1 - Source & expand license-clean fixtures` is sharper on fixture target behavior. Claude explicitly says pothos should aim for breadth with a target of at least 6 independent photos, while Pilea should target at least 3 independent base photos and accept more if available. My draft requires a Pilea minimum and describes breadth, but Claude's target split is more operational.
- `Fallback gate - record the Pilea verdict in the sourcing log` is better than my fallback wording because it distinguishes three states: `>= 3` Pilea fixtures, `1-2` strict-picker-only, and `0` blocked/unmapped. My draft has the same main ideas, but Claude's triage is easier to execute.
- `Phase 3 - Design the disambiguation gate` is more explicit about tradeoffs. The notes under `Candidate A - pairwise top-k delta rule`, `Candidate B - boundary-pair allow-list`, and `Candidate C - Pilea-specific elevated per_species_thresholds` clearly explain why some attractive designs fail the 0.9661 case.
- `Phase 5 - Add the Pilea KB entry + mapping AND lift the CI absence guard in lockstep` is stronger where it calls out the exact new class-map count as `39` in `Update HousePlantClassMapValidationTest.mapsExactlyThirtyEightClasses to the new exact count (39)`. My draft says to update to the new exact count but does not pin it.
- The acceptance item `Pilea is mapped only if the production pothos<->Pilea gate is present and tested (CI-enforced by the new bind-mapping-to-gate test)` is a useful tightening of my equivalent acceptance criterion.
- `Phase 8 - Version bump, APK, gates, docs` includes verifying the Dropbox APK copy via PowerShell. That is a practical addition my draft did not spell out.

## What is weaker than mine

- Claude's `Select the default design: Candidate B` is too decisive before measurement. The brief asks the drafter to weigh and pick/refine a design, so a default recommendation is fine, but Claude's version says the boundary-pair allow-list is "the only honest route" and applies when either Pilea or pothos dominates. That may be too broad if measured true-pothos behavior can still direct-card safely except for raw Pilea top-1 cases. My draft also defaults to a boundary-pair allow-list, but it leaves more room for an optional measured Pilea threshold or narrower routing after evidence.
- `Candidate B - boundary-pair allow-list` underweights the UX and accuracy cost of forcing correct pothos into the picker. It mentions this as a UX regression, but the selected design still seems to force "pothos OR Pilea dominating" into picker. Since pothos is already a mapped species and may have many correct direct-card cases, this may unnecessarily regress the existing pothos route. My draft's risk section frames this as "Pair-forced picker hides correct Pilea cards" but should also have stressed correct pothos; Claude notices it, then still overcommits.
- `Phase 4 - Add the boundary-pair rule to model_manifest.json as data` may be premature. It assumes manifest/config is the best place for `boundary_pairs`. That may be right, but the sprint brief only requires staying behind the frozen seam. My draft's "internal model manifest or mapper configuration" leaves room for the narrowest repo-native implementation after inspecting parser complexity.
- `Phase 5 - Add a license-clean Pilea reference (hero) image ... sourced via the same license discipline (Unsplash/Pexels/Wikimedia)` is weaker because Unsplash/Pexels are not in the brief's allowed fixture license set and their app/use terms are not the same as CC0/PD/CC-BY. For KB reference imagery the brief says license-clean and docs under `docs/licenses/`, but the draft should avoid naming permissive-but-non-CC sources unless the repo already accepts them. My draft simply says license-clean Pilea reference image if required.
- `Repo anchors (verified, for the executor)` may be overconfident. The critique source did not include a repository inspection, only a sprint brief. If these paths are inferred from prior context rather than freshly verified, the word "verified" is risky. My draft avoided claiming verification it had not shown.
- `Phase 8 - (If shipping a public release) push the v0.6.0 tag` adds an optional release-management task absent from the brief. It is not harmful if clearly optional, but the sprint requested a version bump and debug APK, not a GitHub Release/tag decision.
- The Windows sandbox overlay risk in `Risks & mitigations` is likely not relevant to this repo run and distracts from the central product risk. My draft keeps risk focus on fixture licensing, boundary gating, mapping guards, TTA, and seam integrity.

## Missing or under-specified tasks

- Claude should add a clearer task to preserve or update the candidate ordering semantics in the `LowConfidencePicker`. `Phase 4 - Add a candidate-bundle test asserting the boundary low-confidence route surfaces both pilea-peperomioides and epipremnum-aureum` is good, but it should also require that the picker does not bury the true raw top candidate or duplicate candidates when one member of the pair is absent from top-k.
- Claude does not explicitly say to simulate naive Pilea mapping across both clean photos and perturbations before accepting the design. `Phase 2 - Compute ... simulated naive-Pilea-mapped outcome` is present, but it specifically frames "how many pothos fixtures" would surface a confident Pilea card. The no-regression bar needs the naive comparison across all clean photos, all variants, and the boundary subset, not just pothos.
- Claude could make the "8 untested mapped species" task more testable. It says enumerate and source as many as possible, but it does not require a final unsourced-species table with reason codes. My `fixture-sourcing-log.md` task includes rejected near-misses and final per-species counts, which better supports auditability.
- Claude should explicitly require that the old Pilea deferral `_comment` removal does not accidentally weaken other JSON validation semantics. It says rewrite the comment and keep other map guards intact, but the specific risk is that removing a comment-like JSON field changes count assertions or parser expectations. My draft's "without weakening the remaining map validation rules" is slightly clearer as a guardrail.
- Claude does not call out a rollback condition if the selected `Candidate B` increases low-confidence routing unacceptably for already-good pothos while confident-wrong remains flat. The brief's acceptance bar is no confident-wrong regression, but a sprint plan should still require reporting low-confidence route-rate regression, because Candidate B can make the app more abstention-heavy.

## Risks underweighted

- The biggest underweighted risk is over-abstention on correct pothos. `Candidate B - boundary-pair allow-list` explicitly suppresses direct pothos when pothos dominates. That may satisfy "no confident-wrong" while degrading an existing common species. Claude should require a separate pothos direct-card/low-confidence delta in `Phase 6 - Build the comparison table` and an acceptance discussion if the picker rate rises sharply.
- The thin-Pilea sourcing risk is handled well procedurally, but the direct-card calibration risk remains underweighted. Even with `>= 3` Pilea fixtures, a direct Pilea threshold may still be poorly supported. Claude's fallback says `1-2` means strict-picker-only, but `>= 3` should not automatically permit direct Pilea; it should only permit evaluation for direct Pilea. My draft is closer to this by saying Pilea card only when the rule's evidence bar is met.
- `Candidate C - Pilea-specific elevated per_species_thresholds` correctly says the 0.9661 hit can blow past plausible thresholds, but Claude still allows optional C as the direct-card route. The risk is calibration overfit on a tiny Pilea set plus adversarially high pothos false positives. The plan should require held-out or at least author-separated Pilea and pothos evaluation before direct Pilea is allowed.
- The CI Pilea-absence guard lift is mostly safe in Claude, but the underweighted risk is atomicity in practice. `P5 atomic` says one commit/review, but `Phase 4` and `Phase 5` are separate phases and `Phase 4` runs tests before editing the map. The plan should forbid any branch state that maps Pilea without the manifest gate, even transiently in a commit, and make the bind-mapping-to-gate test land before or with the map change.
- The no-regression-on-confident-wrong acceptance bar is present, but Claude could underweight route semantics. A result that routes a true Pilea photo to picker with Pilea visible is acceptable; a result that routes to picker without Pilea visible is not. The acceptance criteria include Pilea visible, but `Phase 6` should also verify candidate visibility and ordering from the actual UI/candidate bundle, not only CSV route.

## Sequencing concerns

- The largest sequencing concern is `Phase 3 - Select the default design` before the TTA sweep. Claude says Candidate D feeds Phase 7 and must be measured, but the default design is selected before the TTA sweep actually runs. The brief's rough sequence puts TTA sweep after gating as supporting work, so this is not fatal. However, the design decision should be "provisional" until baseline and maybe quick TTA evidence show whether x8/x10/x20 materially changes the boundary.
- `Phase 4 - Run testDebugUnitTest ... green before editing the KB map` is correct, but the gate may not be fully testable against the mapped Pilea label until the class-map change exists. The better sequence is to write synthetic mapper tests and a manifest parser test first, then land the bind-mapping-to-gate guard in the same atomic set as the map. My draft's Phase 5 language better emphasizes lockstep over a strict pre-map test boundary.
- `Phase 7 after P1+P4` in the dependency list should probably be after `P6` or at least after the post-mapping gated evaluation exists. Claude's own Phase 7 says compare against the gated x6 production candidate, which implies Pilea mapping and gate are in place. Listing it as after `P1+P4` can be read as allowing the TTA sweep before Phase 5/6.
- `Phase 8 - Update docs/ROADMAP.md` is placed last, which is right, but `docs/kb/ml-mapping-notes.md` is updated in Phase 5 before final post-mapping/TTA evidence. The mapping notes may need a final pass after Phase 6 and Phase 7 so they reflect measured results, not only the design decision.

## If I were merging

I would keep from my draft the more conservative design flexibility around the boundary gate, the cleaner license wording for KB imagery, and the explicit fallback that keeps Pilea unmapped if no clean Pilea fixture can be sourced.

I would keep from the Claude draft the concrete repo anchors, the three-state Pilea sourcing fallback, the sharper candidate-design tradeoff notes, the exact class-map count update to 39, the CI bind-mapping-to-gate test, and the PowerShell verification that the debug APK actually landed in Dropbox.
