# PLANTPOTTING-0012 Codex Draft Critique

(Critique of `PLANTPOTTING-0012-CODEX.md` by the Claude drafter. The gemini draft is
absent — its CLI is quota-blocked — so only the codex draft is critiqued here.)

## Overall read

The codex draft is a solid, faithful execution of the brief. It gets the spine right:
fixtures-first, baseline-before-gate, gate-before-mapping, lockstep guard-lift, post-mapping
no-regression, TTA last. Its phase boundaries match mine almost one-for-one, and on the four
load-bearing areas (disambiguation design, thin-Pilea fallback, lifting the CI absence guard,
the confident-wrong acceptance bar) it lands on the same conclusions I did. Where it differs,
it is generally *less* prescriptive — sometimes that is a virtue (it avoids two overclaims my
draft makes), and sometimes it leaves the executor without the concrete number or verification
step they will actually need.

## What the codex draft does better than mine

- **`Phase 1` splits the two guard checks into separate tasks** — `Run FixtureLicenseManifestTest after adding the first pothos/Pilea fixture batch` and a distinct `Run FixtureIntegrityTest after the fixture batch to catch corrupt images...`. My draft folds both into one bullet. Codex's split is the better operational order: license-vocabulary failures and corrupt-image failures have different fixes, and the executor should clear one class before the next.
- **`Phase 1` sourcing-log task is more audit-complete** — codex asks for `rejected near-misses` alongside accepted files and final per-species counts. My `fixture-sourcing-log.md` task captures accept/reject decisions but codex's explicit "rejected near-misses" framing better supports a later reviewer reconstructing *why* the thin Pilea set ended where it did.
- **`Phase 5` is more lineage-aware about which map guards to preserve** — codex says keep `all verbatim-label, KB resolution, existing-ten, 0009, and 0010 mapping guards intact`. My draft names the actual method symbols (`everyMappingKeyIsVerbatimLabelLine`, `existingTenRowsStillPointAtSameKbIds`, etc.) but does not invoke the 0009/0010 mapping lineage; an executor who thinks in sprint history rather than method names is better served by codex here. (Ideally: merge both — names *and* lineage.)
- **`Phase 5` Pilea reference-image task stays inside the license discipline** — codex says `Add or select a license-clean Pilea reference image only if the KB image resolver requires one`, with attribution under `docs/licenses/`. My equivalent task names `Unsplash/Pexels/Wikimedia` as sources, but Unsplash/Pexels are **not** in the brief's CC0/PD/CC-BY fixture allow-set and carry different use terms. Codex's source-agnostic "license-clean" wording is the safer instruction.
- **It does not overclaim verification.** My draft has a `Repo anchors (verified, for the executor)` heading; the drafting context was a brief, not a fresh repo inspection, so "verified" is risky. Codex folds the same file paths into prose without asserting they were checked. Less convenient for navigation, but more honest.
- **`Phase 4` implementation-location wording is deliberately flexible** — codex says `Extend the internal model manifest or mapper configuration with a pothos/Pilea boundary-pair rule`. My draft commits to `boundary_pairs` as a `model_manifest.json` data block before anyone has read the manifest parser. Codex's "manifest *or* mapper configuration, the narrowest existing score-routing layer" leaves the right call to evidence.

## What is weaker than mine

- **`Phase 3` lists the four candidates but does not reason about them in-plan.** Codex's `Evaluate candidate A/B/C/D` bullets state each mechanism in one line and defer all tradeoffs to `boundary-gating-decision.md`. The brief explicitly asks the drafter to weigh designs *with tradeoffs* — this is THE central challenge. My Candidate A/B/C/D bullets each carry the failure analysis inline (why A's top-k delta misses when pothos isn't even in top-k; why C's elevated threshold can't bite a 0.9661 hit; why B alone over-abstains). Codex's `Reject a margin-only solution if the pothos fixture remains a 0.9661-style single-class confident error` is the one place it reasons, and it's good — but the rest of the design rationale is promised, not shown.
- **`Phase 5` never pins the post-Pilea class count.** Codex: `Update HousePlantClassMapValidationTest.mapsExactlyThirtyEightClasses to the new exact count after Pilea mapping`. Mine pins `39`. Leaving the number implicit invites an off-by-one if the executor miscounts an existing row.
- **`Phase 1` sets no breadth target for pothos.** Codex's `Prefer pothos photos that cover juvenile and mature leaf shape...` is qualitative; my draft commits to `target >= 6 independent photos` for the abundant pothos side and `>= 3 independent base photos` for Pilea. Since pothos supply is ~1470 (abundant) and Pilea ~76 (thin), a concrete breadth floor on the cheap side is exactly where a number helps.
- **`Phase 8` copies the APK but never verifies it landed.** Codex has `Build a debug APK` then `Copy the debug APK to C:\Users\robev\Dropbox\...` with no follow-up. Given the known Windows sandbox-overlay behavior (writes outside the project tree can silently not reach disk), my `verify via PowerShell that the file landed` step is not optional polish — it's the difference between "delivered" and "claimed delivered." This is codex's most consequential omission.
- **`Phase 8` drops the release-tag gotcha.** My draft carries `(If shipping a public release) push the v0.6.0 tag — a versionName bump alone never publishes`. The brief only asks for a version bump + debug APK, so codex is technically in scope, but the project's release.yml fires only on a pushed `v*` tag, and omitting the reminder is how a "released" 0.6.0 silently never appears.
- **No consolidated repo-anchor block.** Codex scatters `ModelScoreMapper`, `model_manifest.json`, `plant_class_map.json`, `HousePlantClassMapValidationTest`, `species.json` across the intro and phases. One executor-facing anchor list (which my draft has, modulo the "verified" overclaim) saves the executor from grepping.

## Missing or under-specified tasks

- **No APK-landing verification task** (`Phase 8`) — covered above; the single most important missing task given the sandbox-overlay risk.
- **No "bind-mapping-to-gate guard must land before/with the map edit, never after" task.** Codex *has* the guard — `Add a test that fails if "Chinese Money Plant (Pilea peperomioides)" is mapped but the pothos/Pilea boundary gate is absent` (Phase 5, strong, keep it) — and `Land the Pilea KB entry... in one commit` in sequencing. But neither phase nor sequencing forbids a *transient* branch/commit state that maps Pilea while the gate guard is not yet present. That transient state is precisely the confidently-wrong window the sprint exists to prevent. My draft has the same gap, so this is a "both should add it," not a codex-only miss.
- **The naive-Pilea simulation is scoped too narrowly.** Codex's `Compute the simulated naive-Pilea-mapped outcome from the baseline CSV` (Phase 2) is good but, like mine, the no-regression bar it feeds needs the naive-vs-gated comparison across **all clean photos, all perturbations, AND the pothos/Pilea subset** — not just the boundary fixtures. The acceptance criterion (line 152) names all three surfaces; the Phase 2 simulation task should explicitly produce all three so Phase 6 can compare like-for-like.
- **No low-confidence-route-rate regression metric.** `Phase 6` builds a comparison table including `low-confidence route rate`, which is good, but there is no acceptance line capping how much MORE abstention the gate may introduce. A correct-pothos input forced into the picker satisfies "no confident-wrong" while quietly degrading a common, previously-direct species. This needs to be a reported-and-bounded number, not just a logged column.
- **The 8 untested mapped species have no final reason-coded outcome table.** Codex's `Inventory the current... 8 mapped species with no clean fixture coverage` (Phase 1) and the sourcing log capture counts, but neither requires a closing table of "which of the 8 got sourced / which stayed uncovered and why." Without it, "sourced as many as possible" is unauditable.

## Risks underweighted

- **Over-abstention on correct pothos is the biggest underweighted risk.** Codex's chosen design — `candidate B, a class-pair allow-list... when either Pilea or pothos dominates above threshold, force the boundary pair into LowConfidencePicker` — by construction suppresses *correct, confident, direct pothos* results, which is an existing common species today. The risk register only frames it as `Pair-forced picker hides correct Pilea cards`; it does not name the pothos-side cost at all. (My draft notices the pothos cost in the design notes but still over-commits to B — so neither of us handles this cleanly, but codex doesn't even flag it.)
- **`>= 3` Pilea fixtures does not equal "direct Pilea card is safe."** Codex's fallback (`If at least 3 independent license-clean Pilea fixtures cannot be sourced... switch... to the fallback path`) is well-worded — and its `instead of forcing a weak Pilea high-confidence route` framing is actually slightly safer than my three-state label, because it implies the gate + evidence still govern even above the threshold. But the risk register should still say plainly: clearing 3 fixtures only earns the *right to evaluate* a direct Pilea card, not the card itself; calibration on ~3–76 photos is intrinsically fragile and wants author-separated / held-out evaluation before any direct route is permitted.
- **No Windows sandbox-overlay risk entry.** The risk section never mentions that the Dropbox APK write may silently not land. Directly tied to the missing Phase 8 verification.
- **Atomicity is asserted in sequencing but not risk-registered.** `Land the Pilea KB entry, mapping, positive guard, and removal of pileaIsNotMapped in one commit` (sequencing) is correct, but the *risk* of a non-atomic landing — and the mitigation that the bind-mapping-to-gate test must be the thing that makes a Pilea-without-gate tree red — isn't called out as a risk with a mitigation.

## Sequencing that is wrong or fragile

- **`Phase 3` selects the default design before the TTA evidence it leans on exists.** Codex's `Evaluate candidate D, TTA/preprocessing-only mitigation: compare whether x6, x8, x10, or x20 changes the pothos/Pilea ranking` sits in the *design* phase, but the apparatus to actually run x8/x10/x20 (`Phase 7 - Add configurable experiment support for TTA x8, x10, and x20`) doesn't exist until five phases later. So the design choice is made against assumed, not measured, TTA behavior. My draft has the identical wrinkle; the honest fix for both is to mark the Phase 3 selection **provisional**, run a quick TTA probe on the boundary subset before finalizing, or explicitly state the gate is chosen independent of TTA (which the 0.9661-no-second-place-mass logic actually supports).
- **`Run the TTA sweep after the expanded fixtures and boundary gate exist` is under-ordered.** Codex's own `Phase 7` task says `Compare each TTA candidate against the gated x6 production baseline` — that "gated production baseline" only exists once Pilea is mapped AND the gate is in (Phase 5) AND post-mapping eval has run (Phase 6). But the dependency line only requires "boundary gate exists" (Phase 4), which would permit running TTA before Phase 5/6. The dependency should read **P7 after P6**, not after P4.
- **`docs/kb/ml-mapping-notes.md` is rewritten in Phase 5, before the measured results land.** Codex's `Update docs/kb/ml-mapping-notes.md to replace the Pilea deferral section with the measured PLANTPOTTING-0012 boundary decision` runs in Phase 5, but the post-mapping confident-wrong numbers (Phase 6) and TTA decision (Phase 7) don't exist yet. The notes need a final pass after Phase 6/7 so "measured boundary decision" reflects actual numbers, not just the design intent. (Mine has the same misorder.)
- **`Run JVM unit tests... before editing the KB map` (Phase 4) is correct but partially un-runnable.** The mapper test that asserts a mapped Pilea label routes low-confidence can't fully exercise the real mapping until `plant_class_map.json` carries the row (Phase 5). Codex covers this with synthetic score rows, which is the right call — but the bind-mapping-to-gate guard genuinely belongs in the *same atomic set* as the map edit (Phase 5), and the sequencing should say so rather than implying everything gate-related must be green strictly before any map edit.

## If I were merging

I would **keep from my draft**: the consolidated repo-anchor list (minus the "verified" claim codex correctly avoids); the per-candidate tradeoff reasoning inside `Phase 3` (the brief's central ask, which codex defers to a doc); the pinned class count `39`; the byte-for-byte "non-boundary species unchanged" mapper test; the `Phase 8` PowerShell verification that the APK actually landed in Dropbox plus the Windows sandbox-overlay risk; and the v0.6.0 release-tag gotcha reminder.

I would **keep from the codex draft**: the source-agnostic `license-clean Pilea reference image only if the resolver requires one` wording (drop my Unsplash/Pexels naming); the split `FixtureLicenseManifestTest` / `FixtureIntegrityTest` tasks; the explicit `rejected near-misses` in the sourcing log; the lineage-aware guard list (`existing-ten, 0009, 0010`) layered on top of my method-name list; the more flexible `manifest or mapper configuration` implementation-location wording instead of my premature `boundary_pairs`-in-manifest commitment; and the safer `instead of forcing a weak Pilea high-confidence route` framing of the thin-Pilea fallback.
